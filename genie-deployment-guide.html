Genie Agents Deployment Guide

What is this guide?

This guide is your roadmap for taking Databricks Genie Agents from a successful proof of concept to a production-grade deployment that serves hundreds or thousands of business users across your organisation.

Whether you are just getting started with Genie Agents or looking to scale an existing deployment, this guide provides practical, step-by-step guidance organised around six key pillars of enterprise readiness.

Note that Genie is the family of Databricks AI experiences. Genie is part of a family of AI experiences built on the same governed data foundation:

  • Genie One (previously Databricks One): A simplified interface for business users to discover and interact with data assets.
  • Genie Agents: Domain-specific environments where data teams configure trusted data, metrics, and business rules that power Genie answers.
  • Genie Code: The AI coding and data assistant for developers and technical practitioners inside the Databricks workspace.

As of November 2026, this guide is focused on Genie Agents, with the Genie One and Genie Ontology context they now work in.

Fast Start

Fast Start

Your 3-part deployment considerations

Enterprise Genie Agent adoption rarely fails due to technology; it fails when organisations scale before their foundations are in place and teams are ready.

Success depends on aligning mindset and execution: focusing on clear business outcomes, demonstrating measurable ROI, and backing delivery with strong executive sponsorship, disciplined project management, and scalable foundations.

This section focuses on three essentials for a successful rollout: getting the foundations right, delivering agents iteratively to drive early value, and sustaining quality as adoption scales.

Part 1: Start Solid with Foundation Checks

A Genie Agent is a Databricks feature that allows business teams to interact with their data using natural language. It uses generative AI tailored to your organisation's terminology and data, with the ability to monitor and refine its performance through user feedback.

Every delivery plan includes an upfront preparation phase. The Success Pillars provide guidance on how to approach each foundational area.

Start these activities early and allow enough time for completion. Treat security sign-off, user onboarding, and identity provisioning as one-time foundational tasks, but don’t let them delay agent development; run them in parallel as separate workstreams.

Part 2: Fast delivery through empowered owners

We recommend iterating in waves, domain by domain, and empowering builders to deliver value regularly. This has a cultural implication: learning to accept good enough quickly and to build on feedback rather than perfect delivery.

Each agent follows the same practitioner lifecycle. Each build should take 1–4 weeks from zero, with best practices in place. The loop does not end at launch, as monitoring, feedback, and curation keep the agent improving continuously.

One rule of thumb above all others: keep each agent to a small number of tables. Focused agents are more accurate than broad agents with 20+ tables. When scope creeps, create a new agent rather than expanding the existing one.

Part 3: The scale-out model

Once you have multiple agents in production, individual attention is not enough. Three practices keep a growing portfolio healthy.

PracticeWhy it matters
Push leftFix data quality and metadata upstream in Unity Catalog; every improvement benefits every agent that shares that data, not just the one you're working on.
Monitor at scaleSet up portfolio-level monitoring early. As adoption grows, catching degrading agents before users notice becomes critical. Use system tables and benchmarks, not just manual spot-checks.
Community of practiceAgent authors sharing patterns, a shared benchmark library, and a quarterly agent health review cadence keep quality high without a central bottleneck.
New

Model the head, let Genie learn the tail. Genie now works on a shared context layer, Genie Ontology, that Genie One and Genie Code both search. Define the business-critical concepts explicitly (top KPIs as metric views, key terms as Pages, assets grouped into Domains, trusted assets certified) and let Genie learn the rest from usage. Genie treats this modeled knowledge as more authoritative than learned knowledge.

Phase 1 - Technical User Validation of the Genie Agent

Once you have a Genie Agent that your creating team is happy with, we recommend you start the final validation process. For the purpose of this phase, we recommend that you actively use the Agent yourselves as Agent administrators, adjust the context as needed (docs), and regularly update and re-run benchmarks if any new questions arise last-minute before the next phase.

  • A limited number of tables (the fewer the better)
  • Tables should have Primary & Foreign Keys set, and table metadata is well documented - columns have clear and precise names and descriptions
  • Entity matching (formerly “Value dictionaries”) helps when users’ prompts do not match the structure or values in the data (e.g., a user prompts “Florida” but the row values are “FL”)
  • Example SQL is in place for the most common types of questions (preferably 10 or more). Parameterised queries are preferred because they can improve answer quality. Where a measure/filter/dimension can be expressed structurally, prefer a SQL Expression in the Knowledge Store over text instructions.
  • Instructions mostly contain business terminology (acronyms, definitions, etc.), specific desired behaviours (e.g. if a prompt mentions X, always follow up until Y is also included), and miscellaneous guidance (e.g., always answer in language XYZ) that cannot be covered by table/column descriptions or Example Queries. If in doubt, always prioritise table/column descriptions and parameterised Example SQL.
  • Benchmarks achieve the desired score: aim for ~80% accuracy; cover the top 15–20 expected user questions with 2–4 phrasings each (~30–80 benchmarks total); agents support up to 500 benchmark questions; use the auto-suggested benchmarks feature to seed

Exit criteria:

  • Benchmarks run at ~80% accuracy over the course of ~1-2 weeks
  • Agent Editors (technical stakeholders) have actively been using the agent for ~1-2 weeks

Phase 2 - Business User Validation of the Genie Agent

Since your benchmarks have been running regularly, it’s time to onboard a handful (~5) of business power users (preferably those who were part of the initial scope definition as key stakeholders) for the business validation step. You don’t need to set up the full access infrastructure just yet - you can give them temporary access to the workspace, with SQL entitlements, and the right permissions to use the agent and run queries (docs).

  • Business power users have had ~1-2 weeks of consistent testing and are satisfied with the answers at this stage of the Agent
  • Any changes needed to be made to the Agent have been done while keeping in mind the steps outlined during Phase 1 - for major changes, restart the timer on the ~1-2 weeks of testing

Exit criteria (can happen in parallel to Phases 3 and 4):

  • Power users have tested the agent for 1-2 weeks without any major changes needed to the agent (you should anticipate ongoing review of user feedback and modification of agent context for the lifetime of the agent)

Phase 3 - Prepare Access and Consumption Layer

You can run some of the administration steps in this section in parallel to Phase 2. You should aim to get in place a robust access management system in place, depending on the preferred way of sharing the Genie Agent at scale within your organisation

  • Choose the preferred way to consume the Genie Agent - in the Genie UI, through a Dashboard Chat Box, or through Customer Web Apps or Teams/Slack integration via the Genie Conversation API (and build if required)
  • Ensure basic permissions are in place for consuming users
    • Define credential methodology - viewer vs. embedded credentials - based on requirements. For the Genie Conversation API path, prefer OAuth over a single PAT token: OAuth preserves per-user UC privileges and per-user usage attribution, whereas a shared PAT loses per-user visibility and is billed as a single identity.
    • If required, set up Automatic Identity Access in Azure
    • If required, set up Share to Account Users (embedded-credentials only): in Public Preview (July 2026), but being functionally superseded by the account-level Genie path below; prefer the GA path below for new builds
    • For business-user consumption without workspace access, the preferred path is the account-level Genie One (formerly Databricks One): supports viewer credentials and a simplified UI on top of the Consumer entitlement; provision via AIM/SCIM. The “Change default workspace access to Consumer access” toggle is in Public Preview (July 2026).

Exit criteria (can happen in parallel to Phases 2 & 4):

  • You have defined (and built, as needed) the way in which business users will interact with Genie

Phase 4 - Put Onboarding & Monitoring Processes in Place

You can run some of the administration steps in this section in parallel to Phase 2. Leverage tooling already available in Databricks to ensure that Agent administrators can actively review the Agent and react to issues in a timely manner, and make sure you publish this information and internal SLAs as part of onboarding users to the Genie Agent:

  • Set up SQL Warehouse monitoring to ensure SLAs are met. General SQL Warehouse monitoring guidance (example blog)
  • Set a schedule on which to address requests for reviews
  • Set up monitoring of Genie Audit events (and alert examples available) to measure spikes in conversations/users - gauge adoption and whether usage is approaching your budgets
  • Leverage the Weekly Monitoring Digest in the Genie Agent Monitoring tab, or consider this community adoption dashboard for Genie Agent-specific observability
  • Define the internal processes of how new users will get access to consume the Genie Agent

Exit criteria (can happen in parallel to Phases 2 & 3):

  • An internal document available to the upcoming users of the Genie Agent that provides them with details about the Genie Agent and its scope, how to request access, how to use Genie to explore business data, as well as the cadence of feedback reviews
  • Alerts are in place to notify the admin team when the SQL Warehouse is breaking defined SLAs
  • Alerts are in place to notify the admin team when usage is reaching the current budgets

Phase 5 - Stage the Rollout to More Users

Validate that Phases 1-4 have been completed before beginning the broader rollout to ensure end users have a positive experience. Define your desired end-state in terms of # of users that will have access to the Genie Agent, as well as what the peaks of concurrency are that you think you’ll reach (e.g. how does peak traffic look during your busiest hours), and work from those numbers backwards. For example, if you think the Genie Agent will be accessible by 500 users in T0 + 2 months, then create a staged roll-out plan that allows you to monitor via the solutions put in place in Phase 4, adjust the Agent based on any unknown questions that come up via the new users, and keep up with the increasing number of manual reviews asked.

We strongly recommend that in the first few weeks, the admin team and the users onboarded work closely to solve any issues that were not preempted in the first two phases. We suggest the following staged approach (starting from your pilot launch date as T0), and only progressing to the next step if there are no changes to the Agent - otherwise, allow for a couple of days in between to mitigate any unpredictable quality changes that could arise due to changes:

  • T0: Reach 10 users in the Agent
  • T0 + 2-3 weeks: Reach 50 users in the Agent
  • T0 + 3-4 weeks: Reach 200 users in the Agent

For subsequent batches, we recommend continuing onboarding in a staged fashion, but do exponential increases after the first couple of stages.

When you are getting close to any of the monitoring limits defined in Phase 4:

  • For SQL Warehouse issues, increase WH size/autoscaling as needed. Follow these guidelines for SQL Warehouse T-shirt sizing.
  • For increases in # of manual reviews needed, ensure you’re staffing the admin team appropriately
  • Since Genie moved to pay-as-you-go (July 2026), there are no fixed questions-per-minute caps on the API. Capacity is shared, so short bursts can return temporary 429 responses: build retries with exponential backoff, and work with your account team if you need dedicated capacity. Use Genie budgets to control spend.
Success Pillars

Why Genie?

Genie lets your business users ask questions in plain language and get answers from your governed enterprise data, no SQL skills required. It bridges the gap between data teams and business users, enabling:

  • Faster time to insight. Business users get answers in seconds, not days.
  • Consistent metrics. Every answer draws from the same governed, curated data.
  • Lower support burden. Routine "Can you pull this data?" requests are handled directly by Genie.
  • Built-in trust. Users can see the SQL behind every answer, and critical queries can be certified for guaranteed accuracy.

Genie isn't a generic chatbot; it is a specialised tool tailored to your organisation's unique data landscape. A production-ready Genie is a governed, trusted, supportable self-service analytics product that:

  • Answers real business questions against curated enterprise data.
  • Respects your existing data governance and security model.
  • Gives business users confidence in the answers.
  • Scales across multiple teams and domains.
  • Has clear ownership, testing, monitoring, and support.

The key shift - in a PoC, the question is "Can Genie answer some good questions?", whereas in production, the question is "Can Genie answer the right questions, consistently, securely, and at scale?".

The most common failure in enterprise Genie adoption is not technical: it is scaling before the foundations are in place and the people are ready. The most common success pattern is getting your foundations right, delivering agents iteratively, and sustaining quality as you scale.

The Six Pillars

The six pillars cover everything an enterprise needs to deploy Genie successfully. Pillars 1 to 5 are foundational; Pillar 6 is optional and only applies if you need to extend Genie outside the native Databricks UI (Teams, Slack, custom apps, embedded experiences).

2. Data FoundationEnsure data quality, metadata, and documentation are production-readyCurated Silver / Gold tables in Unity Catalog; every column has a description; entity matching configured for categorical columns

Through-lines across the pillars

A few themes run across all six pillars and are worth stating explicitly:

  • Foundations before features. A focused, well-documented, governed agent outperforms a broad agent with clever instructions. Pillars 1 and 2 carry more weight than any prompt-engineering trick later in the stack.
  • Unity Catalog is the security boundary, not the Genie Agent. Row filters, column masks, and table grants automatically enforce per-user data access. A Genie Agent defines the curated experience; it is not a hard data boundary.
  • Production-ready is measurable. The ≥80% benchmark-accuracy target is the gate to production. Below that, an agent is not ready regardless of how it feels in a demo.
  • Field-recommended versus Databricks-published. Most adoption targets and review cadences in this guide are field-recommended starting points. Only a high-accuracy gate and the documented product limits are published by Databricks. Calibrate the rest to your organisation.
  • Ownership beats one-off effort. Agents that drift in accuracy do so because no one owns them. A senior analyst or data product owner per agent is the strongest predictor of sustained quality.

Top five ways enterprise rollouts stall

  • Cross-domain agents. Trying to make one agent answer everything. Always less accurate than three focused agents.
  • Skipping benchmarks. Promoting to production without a benchmark suite leaves accuracy invisible and degradation undetectable.
  • Treating Genie as a feature, not a product. No owner, no backlog, no cadence equals quality decay within weeks of launch.
  • Confusing the UI with the security boundary. Hiding columns in the Knowledge Store is not access control. Unity Catalog grants are.
  • Scaling channels before the agent is production-quality. Adding Teams or Slack to a marginal agent amplifies the wrong answers to more users.
1. Business Scope and Agent Design

Pillar 1: Business Scope and Agent Design

Design each Genie Agent for a defined business domain and a known set of user questions. Include the business terms, metrics, and tables required for that domain, and keep unrelated topics out of scope.

Scope limits answer quality. An agent spanning unrelated domains is consistently less accurate than one that stays within its boundaries.

1.1 Design Principles

Keep the agent narrow. Aim for five or fewer tables per agent, with 50 as the hard limit. Use one agent per business domain. Create separate agents for Finance, Sales, Operations, and HR rather than one cross-domain agent. Narrower agents consistently produce better answers.

Before configuration starts, define:

  • The audience.
  • The 20 to 50 business questions the agent should answer.
  • The KPIs and datasets it owns.
  • The topics explicitly out of scope.

State out-of-scope topics in the agent instructions. Treat those instructions as guidance for Genie's behaviour, not as access control. Unity Catalog permissions still govern what users can actually query.

Size by audience:

  • Executive agent: 2 to 3 summary tables with approved metrics.
  • Domain analyst agent: 3 to 5 detailed tables for follow-up questions.

Validate the first 10 to 20 questions against the expected SQL and answers before opening the agent to a wider audience. Expand from there.

Give the agent a clear operating model:

  • Owner
  • Backlog
  • Release cadence
  • Support model
  • Success metrics

1.2 Curation Hierarchy

A Genie Agent improves through layered curation. Use the most structural layer that can express each rule. Reserve text instructions for behaviour that cannot be modelled in metadata or SQL.

  • Unity Catalog metadata: The foundation. Accurate table and column descriptions, primary and foreign keys, and tags help Genie identify the right objects, and the same investment improves every other consumer of the catalog.
  • Metric Views: Live in Unity Catalog, not in the agent. They give a deterministic KPI definition: the calculation is authored once and applied wherever the view is referenced. Any synonyms declared in the metric view's agent metadata are available to Genie. Prefer Metric Views over agent-level SQL expressions when the KPI is shared across multiple agents.
  • SQL expressions: Encode business logic that Genie can use during query generation. Define measures, filters, and dimensions as named expressions so the same logic is reused rather than reinvented per question.
  • Parameterised example SQL queries: Map common question patterns to verified queries. When Genie matches a question to an example, it can use that query directly.
  • Text instructions: Handle formatting, scope reminders, and clarification prompts. They iterate quickly but are open to interpretation, and the Databricks best-practices guidance recommends using them as a last resort when no structural option fits.

1.3 Knowledge Store Configuration

The Knowledge Store holds the agent-specific configuration Genie uses to interpret tables, joins, calculations, and user phrasing in that agent.

It contains:

  • Agent-level metadata customisation: Descriptions for tables, columns, business terms, and synonyms scoped to this agent.
  • Agent-level data customisation: Simplified or focused views of the underlying data without changing the Unity Catalog tables.
  • Prompt matching: Examples that resolve user phrasing to canonical entities, correct common spelling variants, and set output formats.
  • Join relationships: Defined table relationships so JOIN logic is consistent.
  • SQL expressions: Curated measures, filters, and dimensions.

Knowledge Store changes apply only to the current Genie Agent. They do not modify Unity Catalog or any other Databricks asset.

1.4 Sample Questions

Configure 6 to 10 sample questions per agent. They set user expectations on first open and provide working phrasing to start with.

Use the actual metrics, dimensions, and entities the agent owns. Write literal questions, not templated placeholders. For a revenue agent:

  • What was revenue for Q1 2026?
  • Who are the top 10 customers by bookings this year?
  • How does gross margin compare across regions?
  • Show monthly order volume for the last 12 months.
  • Which regions missed the plan last quarter?
  • Break down the pipeline by segment and geography.

Substitute the equivalents for your domain. Where possible, mirror the question patterns covered by your trusted assets so users land on trusted responses from their first interactions.

1.5 Modeled knowledge: Domains, Pages and certification New

Beyond the agent itself, Unity Catalog semantics gives every Genie experience the same business context. Together with metric views these features form the modeled knowledge in Genie Ontology:

  • Domains: a business-aligned layer (for example Finance, Sales, Marketing/User Acquisition) that groups data assets by governed tags on the Discover page. Domains are account-level and support subdomains. Create one domain per agent's business area.
  • Pages: a governed definition of one business concept (a term, KPI or acronym), with owner, synonyms, description, body, related assets and sources. Each Page belongs to one domain. Genie One uses the definition and cites the Page.
  • Certification and deprecation: the system.certification_status tag marks tables, views, metric views, dashboards, Genie Agents, apps and Pages as certified or deprecated, steering Genie One toward the assets your organisation vouches for.
  • Wikis Beta: document a table's meaning, intended use and sources.
  • External knowledge sources Beta: bring measures and relationships from BI semantic models (such as Power BI) into Genie Ontology.

Model the head and let Genie learn the tail: start with the KPIs and terms that must be right, then expand.

2. Data Foundation

Pillar 2: Data Foundation

Genie depends on clear metadata, consistent structures, and governed data to turn natural-language questions into accurate SQL queries. It uses your table and column metadata to identify the right dataset, measures, dates, and joins.

For a question such as "What were total sales last quarter?", Genie must understand:

  • Which table contains the sales data?
  • Which column holds the sales amount?
  • Which column defines the date?
  • How the relevant tables relate to each other.

If that context is missing or unclear, Genie is more likely to generate incorrect SQL. Validate each agent with representative benchmark questions before production.

2.1 Data Layer Recommendations

Use cleaned, curated data rather than raw ingestion tables.

  • Raw / Bronze: avoid. Quality issues, cryptic column names, and incomplete records make Genie unreliable.
  • Cleaned / Silver: use. Validated, standardised, consistent data types.
  • Aggregated / Gold: prefer. Optimised for analytics, clearer business logic, pre-calculated metrics.

2.2 Preparation Checklist

Preparation happens at two levels: each table in Unity Catalog, and then the Genie Agent that uses them.

Per table (Unity Catalog)

Must have

  • Register the table in Unity Catalog.
  • Add a table comment that explains the contents and business context.
  • Add a clear business description for every column.
  • Use self-explanatory column names. Prefer customer_lifetime_value over clv.
  • Store date fields as DATE or TIMESTAMP, not strings.

Should have

  • Define primary and foreign key relationships.
  • Apply Unity Catalog governance tags for PII and sensitivity classification.

Good to have

  • Run OPTIMIZE, unless predictive optimisation is enabled.
  • Document the data freshness cadence.

Per agent (Knowledge Store and ACLs)

Must have

  • Apply Unity Catalog permissions on the underlying data, and configure Genie Agent ACLs on the agent itself.

Should have

  • Keep each agent to five or fewer tables where possible. Treat 50 tables, views or metric views as the hard limit.
  • Pre-join frequently joined tables into views, or define join relationships in the Knowledge Store.
  • Enable entity matching on categorical columns (regions, statuses, product names) so Genie maps user phrasings to canonical values.
  • Enable format assistance on important columns to give Genie representative sample values.

Good to have

  • Hide unnecessary or confusing columns in the Knowledge Store.

2.3 Metric Views

Metric Views are useful when one KPI definition needs to apply consistently across teams, dashboards, and Genie Agents. Define a metric once, then let users query it by region, time period, or product line without rewriting the calculation each time.

When Genie answers from a Metric View, it uses the approved definition rather than a locally recreated formula. Adopt Metric Views when you have a shared set of standardised KPIs referenced across multiple teams or reports.

New Add agent metadata to each metric view: display names, synonyms and format specifications. Genie uses the synonyms to map the words people use to the right measure or dimension, so you do not repeat them in every agent. Certify the metric views your agents rely on.

2.4 Data Quality Gates

Before adding a table to a production Genie Agent, verify the following:

2.5 Discoverability and trust signals New

  • Tag the curated schemas and tables with the governed tag of their domain so they appear on the Discover page and in Genie One under the right business area.
  • Certify the gold tables and metric views that agents use, and deprecate the legacy tables they replace, with certification and deprecation.
  • Define the key terms each agent depends on as Pages in that domain.
  • On workspaces with the compliance security profile, the Discover page is disabled by default; a workspace admin must enable it to use domains.
3. Governance & Security

Pillar 3: Governance & Security

Genie respects Unity Catalog automatically: your existing access controls, row-level security, and data-classification policies apply to Genie responses without re-configuration. This pillar covers the deployment patterns, controls, and review steps that preserve that posture in production.

3.1 How Genie Executes Queries: Credential Models

Genie generates read-only SQL from natural-language questions and runs it on a SQL warehouse. The identity under which the query runs depends on the deployment pattern.

Important. A Genie Agent defines what users see in the UI: the tables, instructions, and examples available to them. It is not a hard data boundary. Unity Catalog permissions, row filters, and column masks define what each user can actually query. Rely on Unity Catalog grants for access enforcement, not on agent composition alone.

3.2 Unity Catalog: Your Primary Security Layer

All Genie queries are governed by Unity Catalog. This means:

ControlHow It Works
Table and view grantsA Genie Agent can only query objects on which the user has SELECT access.

3.3.1 Consumer access and Genie

Two related but distinct concepts:

  • Consumer access is a workspace entitlement for non-technical business users. It activates Genie, dashboards, Databricks Apps, and related AI/BI experiences without requiring authoring entitlements (Workspace access or Databricks SQL access).
  • Genie One (previously Databricks One) is the simplified UI that consumer-access users land in. It focuses on consumption: no SQL editor, no notebooks, only dashboards and Genie agents.

Key benefits

  • Genie One and Genie Agents usage by users is free through January 31, 2027; service principal usage is billed. SQL warehouse compute is billed separately. See Monitor Genie cost.
  • Simplified interface for business users.
  • Provision users via your identity provider (Azure AD, Okta, and similar).

3.3.2 Onboarding business users to Genie

  • Provision users at the account level.
    • Add users through Automatic Identity Management.
    • Ensure users exist in the Databricks account before assigning the workspace.
  • Assign users to the right workspace with consumer access.
    • Add the users to the target workspace.
    • Grant consumer access to Genie, dashboards, and related shared assets without authoring permissions.
  • Enable a custom URL (optional).
    • Optionally enable a custom URL for the workspace.
    • Recommended to simplify the login experience across workspaces.

3.3.3 Access Configuration Checklist

  • Unity Catalog permissions reviewed for all Genie Agent tables.
  • Row filters applied where needed (region, department, and similar).
  • Column masks applied for sensitive data (PII, compensation, and similar).
  • Agent permissions set.
  • Audit logging enabled and reviewed.
  • Dashboard dataset scope reviewed for companion agents.
  • Credential model documented for each deployment pattern.
  • Consumer access is configured for business users.

4.3 Prompt Guide Template

Create a prompt guide for each agent with the following sections.

Good question patterns

  • "What was total revenue by region last quarter?"
  • "Show me the top 10 customers by lifetime value."
  • "How does this month's churn rate compare to last month?"

Tips for better answers

  • Be specific about time periods, filters, and metrics.
  • Use the business terms defined in your agent, for example, "ARR" rather than "annual recurring revenue" if that is the configured synonym.
  • Start simple, then add complexity.

Out-of-scope topics

4.4 Building Trust

  • Transparency. Show users the SQL behind every answer, and encourage them to verify against known reports.

  • Feedback loops. Make it easy to report incorrect answers and show that user feedback drives improvements.
  • Gradual expansion. Start with a small group of power users, then expand as confidence grows.

5. Monitoring & Continuous Improvement

Pillar 5: Monitoring & Continuous Improvement

Maintain and improve Genie quality after launch. This pillar covers the monitoring, feedback, benchmarking, and review practices that keep an agent accurate and useful over time.

5.1 Monitoring Tools

Databricks provides built-in monitoring at multiple levels through the Monitor tab, audit logs, and system tables.

5.1.1 Monitor tab

For agent owners, the Monitor tab helps you:

  • View every question users have asked.
  • See which questions received positive or negative feedback.
  • Identify patterns, including which questions the agent struggles with.
  • Review requests where users have flagged responses that need attention.
  • Track weekly digest signals: message volume, active users, and thumbs-up / thumbs-down rates.

Important. Thumbs up / thumbs down do not automatically change the agent. Authors review feedback and decide what to act on.

5.1.2 Audit logs

Audit logs (captured in system.access.audit with service_name = 'aibiGenie') help you:

  • Track who accessed which agents and when.
  • Monitor conversation volumes and user activity trends.
  • Set up alerts for unusual patterns such as spikes in negative feedback, approaching budgets, or rising error rates. Alerts are configured as Databricks SQL Alerts on queries against the audit system tables; there is no Genie-native alert mechanism.

5.1.3 System tables

System tables expose Genie activity for analysis and cost attribution:

  • system.query.history: all Genie-generated SQL queries, their duration, and success or failure rates. Filter for Genie traffic with WHERE query_source.genie_space_id IS NOT NULL, or for a single agent with WHERE query_source.genie_space_id = '<space-id>'.
  • system.billing.usage: cost of Genie usage via SQL warehouse consumption.
  • system.compute.warehouse_events: compute scaling events triggered by Genie query load.
  • system.access.audit: per-event audit records (also surfaced in 5.1.2 above).

5.2 The Feedback-to-Curation Loop

User feedback is the primary signal for keeping Genie quality high over time. Treat it as a repeatable operating loop rather than an occasional clean-up task.

  • Capture feedback from the Monitor tab: thumbs-up / thumbs-down signals, review requests, and recurring unanswered questions.
  • Triage the feedback by separating one-off issues from repeatable gaps, and prioritise questions tied to important business workflows.
  • Curate the agent by updating instructions, adding Trusted Assets, and expanding entity matching when users introduce new terminology.
  • Validate the change by rerunning the relevant benchmark questions and checking whether the issue is resolved without breaking existing coverage.
  • Apply and observe. Record the change in the curation log, then monitor the same question patterns to confirm the improvement holds.

5.3 Benchmarking: Measuring Accuracy Systematically

Benchmarks are a quality-assurance framework for Genie Agents. Use a benchmark suite of representative business questions, each with multiple phrasings, paired with their expected correct SQL answers. Run the suite against the agent and measure the percentage of Genie's predictions that are correct.

Databricks recommends aiming for 10 to 20 representative questions, with 2 to 4 phrasings each (roughly 30 to 80 benchmarks total). The product supports up to 500 benchmarks per agent.

5.3.1 How to Use Benchmarks

  • Create a benchmark suite covering the most important question categories.
  • Run the suite after every significant change to instructions or data.
  • Track accuracy over time; it should trend upward.
  • Use benchmarks as a gate: do not promote an agent to production unless it achieves ≥80% accuracy.
  • Use Auto-suggested benchmarks to bootstrap the suite. Genie can suggest test questions based on the agent's tables, columns, and SQL examples.

5.3.2 Key Metrics to Track

The ≥80% benchmark-accuracy target is Databricks-published guidance. The other metrics below are field-recommended signals; calibrate the targets to your organisation.

The cadence below is a field-recommended starting point. Calibrate it to the maturity of the agent and the volume of user feedback.

Weekly

  • Review the Monitor tab for new question patterns.
  • Check for questions with negative feedback.
  • Note questions Genie could not answer.

Every two weeks

  • Add new Trusted Assets for frequently asked questions.
  • Update entity matching if users introduce new terminology.
  • Address any review requests from users.

  • Add Teams, Slack, or custom integrations after the agent is production-quality, for specific business cases that need them.

6.3 Conversation API for Custom Experiences

The Conversation API lets you embed Genie in custom applications, chatbots, and portals. The same surface area also exposes the Genie Agents management APIs for creating, configuring, backing up, and promoting agents across workspaces.

Key capabilities

  • Start and continue multi-turn conversations programmatically.
  • Send questions and receive structured responses.
  • Retrieve generated SQL, query results, message status, and metadata.
  • Manage Genie Agent configuration through the management APIs.

Authentication options

  • OAuth M2M for service principals, for server-side applications and unattended workloads.
  • OAuth U2M for users, when a browser-based user flow is available.

Best practices for API integration

  • Poll message status every 1 to 5 seconds until you receive a conclusive state, such as COMPLETED, FAILED, or CANCELLED.
  • Use exponential backoff for retries and polling, increasing the delay up to one minute for long-running queries.
  • Start a new conversation for each user session to avoid unintended context reuse, which can reduce accuracy.
  • Implement request queuing, retry logic, and logging in the calling application.
  • Stop polling after about 10 minutes for most queries, then return a timeout or manual follow-up path.
  • Stay under the limit of 200,000 conversations per agent: list and delete old or test conversations with the API.
  • Render charts in your own UI if needed. The API returns structured tabular results and SQL, not rendered visualisations.

Planning considerations

  • Use the minimum-privilege identity model for each integration.
  • Curate and benchmark the Genie Agent before exposing it through the API.
  • Plan SQL warehouse capacity explicitly. Every Genie query still runs on the attached warehouse.
  • Expect some lag between new UI features and API availability.
  • Use the management APIs to export and recreate agent configuration across environments.

6.4 Environment Promotion

For enterprise deployments, keep promotion explicit and repeatable:

  • Use the Genie Agents management APIs to move agent configuration between environments. If you already standardise delivery with Declarative Automation Bundles (previously Databricks Asset Bundles), keep the surrounding deployment workflow in the same promotion pipeline. Bundles support Genie Agents natively: the genie_spaces resource (Databricks CLI 1.3.0 or later, direct deployment engine) deploys an agent from a .geniespace.json file kept in Git, and databricks bundle generate genie-space exports an agent built in the UI. See genie_space resource and the Genie Agent CI/CD example (dev, staging and prod with a benchmark gate). The management APIs remain available for custom pipelines.
  • Maintain separate catalogues for dev, staging, and production data.
  • Re-run benchmarks before every promotion.

6.5 One front door across agents: Genie One

For organisations with many Genie Agents, Genie One is the conversational entry point: it searches the available Genie Agents for one relevant to the question, and otherwise searches the data assets the user can access, citing its sources. Answers always run as the asking user, so Unity Catalog permissions, row filters and column masks apply.

Keep agents few, focused and well described, and use domains and certification so Genie One routes well; the documentation notes that many overlapping agents reduce routing accuracy. To coordinate agents in code with custom routing, use the Agent Bricks CLI. The Agent Bricks Supervisor Agent is now a legacy offering and is not recommended for new systems.

6.6 Throughput Planning

For API-based integrations, plan on observed demand rather than theoretical peak usage.

Key insight. In practice, the concurrent query rate is much lower than the peak user count. This is because:

  • Users pause to read and interpret results between questions.
  • Load tends to arrive in short bursts rather than as a continuous stream.
  • Application-side caching and queuing can reduce the number of repeated calls.
  • Time-zone distribution often smooths demand in larger deployments.

Recommended approach

  • Start with a small pilot cohort and measure actual query patterns.
  • Monitor peak concurrent queries per minute over at least 30 days.
  • Right-size capacity using observed traffic, not headline user counts.
  • Scale incrementally as adoption expands.

Throughput

  • Genie moved to pay-as-you-go in July 2026 and no fixed questions-per-minute caps apply to the Databricks UI or the Conversation API.
  • Capacity is shared: design for temporary 429 responses during spikes with retries and backoff.
  • Real throughput is set by the SQL warehouse behind the agent; queries running longer than five minutes are cancelled.
  • For dedicated capacity, contact your Databricks account team.
